01 / Conceptual model

Layered cloud architecture design

Architectural Hierarchy & The Hotel Analogy

A cloud computing platform is organized as a structured 5-layer engineering hierarchy. User requests travel downward through the layers, while data, telemetry, and billing metrics flow upward.

The Luxury Hotel Analogy:

  • User & Access Layer: The front reception desk where guests authenticate with passports and receive digital room keycards.
  • Service Layer: The room packages offered to guests (e.g., standard room, executive suite, or villa).
  • Orchestration Layer: The hotel management system scheduling housekeeping, allocating vacant rooms, and coordinating room service.
  • Resource Abstraction Layer: Room furniture, air-conditioning, and plumbing pipes partitioned dynamically among rooms.
  • Physical Layer: The concrete foundation, steel framing, electrical generators, and plumbing pipes of the physical building.
  • Cross-Cutting Controls: Fire alarms, CCTV security, billing systems, and privacy policies apply across every single floor and room.

Responsibilities of Each Architecture Layer

  1. User and Access Layer: The gateway into the cloud. Manages identity authentication, role-based authorization (IAM), web management consoles, command-line interfaces (CLI), and public API gateways.
  2. Service Layer: Delivers the functional capabilities rented by consumers, ranging from complete enterprise applications (SaaS) to managed developer runtimes (PaaS) and virtualized infrastructure (IaaS).
  3. Orchestration Layer: Translates high-level provisioning policies into runtime operations. Automates instance placement, horizontal auto-scaling during traffic spikes, and node self-healing.
  4. Resource Abstraction Layer: Decouples software workloads from physical hardware using hypervisors, software-defined networks (SDN), and block storage controllers.
  5. Physical Layer: Physical data center assets: high-density compute blades, multi-terabit optical network fabrics, backup generators, and cooling infrastructure.

02 / Standard reference

NIST SP 500-292: actors and reference architecture

Distinction Between NIST Standards

  • NIST SP 800-145: The Cloud Computing Definition (5 Characteristics, 3 Service Models, 4 Deployment Models).
  • NIST SP 500-292: The Cloud Computing Reference Architecture (5 Major Actors / Roles in the cloud ecosystem).
NIST SP 500-292: The 5 Cloud Actors Reference Architecture
Actor 1 Cloud Consumer

Person or organization that maintains a business relationship with, and uses services from, providers.

Actor 2 Cloud Provider

Entity responsible for operating infrastructure and making cloud services available to consumers.

Actor 3 Cloud Broker

Intermediary managing use, performance, aggregation, and integration between consumers and providers.

Actor 4 Cloud Auditor

Independent party assessing security, operations, SLA performance, and privacy compliance.

Actor 5 Cloud Carrier

Telecom network intermediary providing physical transport and connectivity between parties.

The 5 NIST SP 500-292 Actors: Roles and Enterprise Examples
ActorFormal NIST DefinitionOperational RoleReal-World Enterprise Example
1. Cloud Consumer Person or organization that maintains a business relationship with, and uses service from, Cloud Providers. The tenant or client consuming computing services for business workloads. Netflix, Airbnb, University: Runs video streaming or student portals on AWS/Azure infrastructure.
2. Cloud Provider Person, organization, or entity responsible for making a service available to interested parties. The owner and operator of the physical and virtual cloud infrastructure. AWS, Microsoft Azure, Google Cloud (GCP): Operates hyper-scale data centers globally.
3. Cloud Broker An entity that manages the use, performance, and delivery of cloud services, negotiating relationships between providers and consumers. Consultancy or aggregator integrating multiple clouds for cost and performance optimization. Accenture, Wipro, CloudHealth: Coordinates multi-cloud migrations, aggregates billing, and manages arbitrage.
4. Cloud Auditor A party that conducts independent assessment of cloud services, information systems, performance, and security. Independent inspection agency verifying standards compliance. Deloitte, PwC, Ernst & Young, KPMG: Conducts audits verifying SOC 2 Type II, ISO 27001, and HIPAA controls.
5. Cloud Carrier An intermediary providing connectivity and transport of cloud services from providers to consumers. Telecom carrier maintaining physical high-speed fiber-optic routes. AT&T, Verizon, Tata Communications, Airtel: Provides dedicated AWS DirectConnect and Azure ExpressRoute links.

The 3 Specialized Functions of a Cloud Broker

  1. Service Intermediation: Enhances a specific service by adding capabilities, such as managing access identities, data tokenization, or encryption before transport.
  2. Service Aggregation: Combines and integrates multiple distinct cloud services into unified workflows (e.g., combining AWS EC2 compute, Twilio SMS API, and Stripe payments into an e-commerce platform).
  3. Service Arbitrage: Dynamically routes customer workloads to whichever cloud provider offers the lowest spot price or lowest network latency at that moment.

03 / Ownership and placement

Deployment models: who uses the cloud?

Deployment Paradigms & Transportation Analogy

A Cloud Deployment Model defines the ownership, accessibility, and operational boundary of cloud infrastructure:

  • Public Cloud (City Bus): Open to all ticketed passengers. Multi-tenant seats shared among the general public; highly cost-effective and elastic, operated on public routes.
  • Private Cloud (Private Car): Exclusive use by one household. Maximum customization, dedicated control, and total privacy; owner bears all capital and maintenance costs.
  • Hybrid Cloud (Commuter Car + Commercial Flights): Use a personal car for routine local travel (sensitive internal records), and take commercial flights for long-distance peak travel (public cloud elasticity).
  • Community Cloud (Gated Community Shuttle): A shared transit vehicle operating exclusively for residents of three neighboring luxury societies sharing common security guidelines.
Comparison of the 4 Cloud Deployment Models
ModelTenancy & OwnershipKey StrengthsMajor ConstraintsTarget Workload Scenario
Public Cloud Owned and operated by third-party providers (AWS, Azure, GCP). Shared multi-tenant infrastructure. Zero upfront CapEx, rapid elasticity, global availability zones, zero hardware maintenance. Limited physical placement control; data sovereignty compliance requires careful architectural governance. Startups, e-commerce platforms (Flipkart, Amazon), streaming media (Netflix), public web applications.
Private Cloud Exclusively provisioned for one organization. Can be hosted on-premises or by a third party. Complete hardware control, dedicated hardware isolation, straightforward compliance with defense or sovereign mandates. High capital expenditure (CapEx) to purchase and refresh hardware; finite capacity limits elasticity. National defense agencies, central bank settlement ledgers (e.g., Reserve Bank of India, Federal Reserve).
Hybrid Cloud Composition of two or more distinct clouds (private and public) bound by standardized interoperability. Maintains sensitive databases on private hardware while bursting web traffic into public clouds during spikes ("cloud bursting"). High networking complexity: requires secure VPN/DirectConnect tunnels, federated IAM, and latency management. Commercial banks: sensitive customer ledgers remain on-premise; mobile banking frontends scale elastically on AWS.
Community Cloud Infrastructure shared exclusively by several organizations with shared compliance or regulatory requirements. Costs are shared among participating organizations; customized compliance tailored to a specific industry. Requires collaborative governance, multi-party cost-sharing agreements, and coordinated upgrade cycles. Consortium of regional hospitals sharing a HIPAA-compliant medical research cloud; municipal government bodies.

04 / Responsibility boundary

IaaS, PaaS, SaaS, and modern service models

The Pizza-as-a-Service Analogy

The division of operational responsibility across cloud service models aligns with how dining is sourced:

  • Traditional On-Premise IT (Homemade from Scratch): You buy flour, knead dough, prepare toppings, provide the gas oven, dining table, and clean up. You manage every layer.
  • IaaS (Take-and-Bake Pizza): The store provides the dough, crust, and sauce (raw servers, storage, networking). You provide the oven, set baking temperatures, and serve. (You manage OS, runtime, and applications).
  • PaaS (Pizza Delivered to Your Door): The pizzeria prepares ingredients and bakes the pizza. You provide the table and drinks. You focus on eating (deploying application code), not operating the oven (OS/hardware).
  • SaaS (Dining at a Pizzeria): You walk in, sit at a table, eat, pay, and walk out. The restaurant manages kitchen, dining tables, electricity, and clean up. You simply use the finished application.

05 / Architecture & Governance

Architectural challenges & cloud security

1. High Availability & Service Level Agreements (SLAs)

Cloud availability is measured in "Nines" of uptime:

Cloud Availability Metrics and Permissible Annual Downtime
Availability PercentageDesignationMaximum Allowed Downtime per YearArchitectural Mechanism
99.0%"Two Nines"3.65 days / yearSingle server instance without automated failover.
99.9%"Three Nines"8.77 hours / yearStandard cloud VM with automated snapshot backups.
99.99%"Four Nines"52.6 minutes / yearMulti-Availability Zone (Multi-AZ) clustering behind an Elastic Load Balancer.
99.999%"Five Nines"5.26 minutes / yearActive-Active Multi-Region deployment with automated global DNS failover (Route 53).

2. Multi-Tenancy & The "Noisy Neighbor" Problem

In a multi-tenant cloud, if VM-A executes an intensive cryptographic calculation or memory-bound workload that saturates shared CPU caches and memory buses, neighboring VM-B on the same physical host may experience latency spikes. Hypervisors mitigate noisy neighbors through CPU Pinning, cgroups bandwidth throttling, and hypervisor resource reservations.

3. Key Enterprise Cloud Security Standards

  • ISO/IEC 27001 & 27017: Global baseline for Information Security Management Systems (ISMS), specifying controls for cloud data protection and multi-tenant isolation.
  • SOC 2 Type II: Independent third-party audit assessing a provider across 5 Trust Principles: Security, Availability, Processing Integrity, Confidentiality, and Privacy.
  • PCI DSS: Mandatory technical baseline for any cloud architecture storing, processing, or transmitting payment card numbers.
  • HIPAA: US federal legislation mandating cryptographic controls and audit trails for Protected Health Information (PHI) in cloud medical systems.

4. Mitigating Insider Threats: Zero Trust Architecture

A critical cloud risk is the Malicious Insider (a compromised staff credential or rogue administrator). Modern cloud security counters this with:

  1. Zero Trust Architecture (ZTA): "Never Trust, Always Verify." Being inside the network perimeter grants zero implicit privileges. Every API call must be authenticated, authorized, and encrypted.
  2. Principle of Least Privilege (PoLP): Users and service accounts receive only the minimal permissions necessary for their specific role.
  3. Privileged Access Management (PAM) & Just-In-Time (JIT) Elevation: Engineers lack permanent root access. Emergency maintenance requires temporary, time-limited credentials approved by multiple parties.
  4. WORM Audit Logging (Write Once, Read Many): Administrative actions are committed to immutable, tamper-proof logs (e.g., AWS CloudTrail locked via S3 Object Lock) that cannot be altered even by root administrators.

06 / Data persistence

Cloud storage paradigms: block, file, and object

Cloud systems provide three distinct storage abstractions optimized for different access patterns, latency constraints, and data structures:

Comparative Matrix: Block Storage vs File Storage vs Object Storage
DimensionBlock StorageFile StorageObject Storage
Underlying Model Raw, unformatted storage sectors carved into fixed-size blocks (e.g., 512-byte or 4 KB blocks) without an inherent filesystem. Hierarchical directory tree structure of folders and files (e.g., /home/user/docs/report.pdf). Flat, non-hierarchical address space. Data is stored as an Object containing payload, unique Key, and extensible metadata.
Analogy A blank physical SSD or hard drive formatted with NTFS/ext4 to host an OS. A shared office filing cabinet where documents are stored in labeled folders. A coat-check ticket: hand over a coat, receive a claim ticket (Key), retrieve the exact item via the ticket.
Access Protocol Storage protocols: iSCSI, Fibre Channel, NVMe-oF. Network File Sharing protocols: NFS (Linux), SMB/CIFS (Windows). Web APIs over HTTP/HTTPS REST (GET, PUT, DELETE, POST).
Latency & Speed Sub-millisecond latency: Highest IOPS; direct block-level access. Moderate latency: POSIX locking and metadata directory traversal overhead. Higher latency (tens of milliseconds), but virtually infinite throughput and massive parallel scalability.
Cloud Products Amazon EBS, Azure Managed Disks, Google Persistent Disk. Amazon EFS, Azure Files, Google Cloud Filestore. Amazon S3, Google Cloud Storage (GCS), Azure Blob Storage.
Best Use Case High-performance transactional databases (Oracle, PostgreSQL, MySQL) and VM boot drives. Shared enterprise user directories, legacy applications, content management media folders. Petabytes of unstructured multimedia: photos, videos, mobile app backups, data lake analytics (Hadoop/Spark).

07 / Storage implementation

Amazon S3 (Simple Storage Service) deep dive

Overview

Launched in March 2006, Amazon S3 was AWS's first commercially available cloud service. It provides internet-scale, highly durable object storage designed to store and retrieve arbitrary data from anywhere on the web.

The 4 Core Architectural Concepts of Amazon S3

  • 1. Buckets: The root container for storing objects in S3. Every bucket must possess a globally unique name across all AWS accounts worldwide (e.g., https://my-bucket.s3.amazonaws.com). Buckets define the physical geographic region where data is persisted.
  • 2. Objects: The fundamental entity stored in S3, consisting of:
    • Data Payload: The file content (from 0 bytes up to 5 Terabytes per single object).
    • Key: The unique string identifier (the "path/filename", e.g., images/2026/convocation.jpg).
    • Metadata: Key-value pairs containing system attributes (Content-Type, creation date) and custom tags.
    • Version ID: Enabled via bucket versioning to safeguard against accidental overwrites or deletes.
  • 3. REST API Operations: Data is manipulated purely via HTTP:
    • PUT /bucket/key — Upload an object.
    • GET /bucket/key — Download an object.
    • DELETE /bucket/key — Delete an object.
  • 4. 11 Nines of Durability (99.999999999%): S3 synchronously replicates every object across a minimum of 3 separate physical Availability Zones within the region. Storing 10,000,000 files in S3 yields an expected loss of 1 file every 10,000 years.

08 / Applied design

Worked cloud architecture scenario

Enterprise Case Study: Architecture for a Global Photo App (e.g., Instagram)

Examination Scenario: Design a secure, highly scalable, cost-effective cloud architecture for a photo-sharing platform serving 50 million active users. Justify your selection of service models, deployment models, and storage tiers.

Applied Cloud Architecture: Global Photo Service End-to-End Pipeline
Ingress Mobile App

Clients connect through Amazon CloudFront CDN edge locations globally.

Routing API Gateway

Throttles traffic, validates JWT authentication, and routes requests.

Processing AWS Lambda (FaaS)

Event-driven resizing of uploaded photos into multiple resolutions.

Persistence S3 + DynamoDB

Photos in Amazon S3; image metadata in low-latency DynamoDB tables.

Architectural Choices & Justifications

  1. Deployment Model: Public Cloud (AWS). Elastic scaling absorbs viral traffic spikes without purchasing fixed data center hardware. Global CDN edge locations deliver low latency worldwide.
  2. Compute Model: Serverless FaaS (AWS Lambda) + Microservices.
    • When a user uploads a photo, an S3 event trigger automatically invokes an AWS Lambda function.
    • The function generates thumbnail and web-optimized resolutions in 400 milliseconds, saving them back to S3. Zero compute charges occur during idle hours.
  3. Storage Architecture: Object Storage (Amazon S3) + Managed NoSQL (DynamoDB).
    • Photos (unstructured binary data) reside in Amazon S3.
    • Photo metadata (User ID, GPS location, tags, upload timestamp, S3 object URL) is indexed in Amazon DynamoDB for single-digit millisecond queries.
    • S3 Lifecycle policies automatically move photos older than 180 days to S3 Standard-IA, cutting storage costs by 45%.
