01 / Unit I

Foundations and cloud characteristics

See Unit I for the full definition, worked examples and distinctions.

Cloud computing
A model for on-demand network access to pooled configurable resources that can be rapidly provisioned and released with minimal provider interaction. NIST defines five essential characteristics, three service models and four deployment models; remotely hosted software alone is not sufficient to establish all five characteristics.
Time-sharing, cluster, grid, utility computing
Time-sharing shares one computer among users. A cluster coordinates machines for performance or availability, usually under a common administration; a grid federates resources across sites or organizations. Utility computing treats capacity as a metered service. These are historical and conceptual contributors to cloud computing, not equivalent definitions.
Parallel versus distributed computing
Parallelism executes work simultaneously, possibly on several cores of one machine; distribution coordinates independent networked computers with separate memory and failure modes. A distributed job can also be parallel. Data parallelism applies one operation to partitions; task parallelism runs different operations concurrently.
Amdahl’s law
For a fixed-size job with parallelizable fraction p and N identical workers, ideal speedup is S(N) = 1 / [(1 − p) + p/N]. If p = 0.8 and N = 4, speedup is 2.5, not 4; communication can reduce it further.
On-demand self-service
A consumer provisions capabilities such as compute or storage automatically as needed, without human interaction for each request with the provider. Approval policies and quotas can still apply.
Broad network access
Capabilities are available over the network through standard mechanisms supporting heterogeneous clients, such as phones and laptops. This does not guarantee equal speed or continuous connectivity.
Resource pooling
Shared provider resources serve multiple consumers; physical and virtual capacity is dynamically assigned and reassigned. Isolation and authorization are required; shared infrastructure does not imply shared customer data.
Rapid elasticity
Capacity can be provisioned and released rapidly, sometimes automatically, in response to demand. It may appear unlimited to a consumer, although real quotas, capacity and provisioning delays remain.
Measured service
Usage is monitored, controlled, reported and metered at a service-appropriate level, for example GB-months, processing time or active accounts. Metering is a characteristic; it does not specify a universal billing interval.
Scalability versus elasticity
Scalability is the ability to handle increased load by adding capacity or improving architecture. Elasticity adjusts allocated capacity upward and downward as demand changes. A system can scale to a fixed peak without releasing resources when traffic falls.
Vertical versus horizontal scaling
Vertical scaling adds capacity to one machine; horizontal scaling adds machines. Horizontal scaling requires suitable workload partitioning, shared-state design and load distribution; neither mode is automatically elastic.
On-demand provisioning and autoscaling
Provisioning makes a requested resource usable and release returns its allocation. Autoscaling is policy-driven adjustment based on signals such as request rate or CPU use. It needs sensible thresholds, minimums, maximums and an application that can tolerate instance additions and removals.
On-demand vs Reserved vs Spot instances
On-Demand: Pay per hour/second with no commitment; maximum flexibility. Reserved: 1- or 3-year commitment for steady workloads; 40%–72% discount. Spot: Dynamic auction of spare capacity; up to 90% discount, but can be preempted on 2-minute notice.
Flynn's taxonomy
Classification of computer architectures by concurrent instruction and data streams: SISD (traditional uniprocessor), SIMD (vector/GPU parallel processing), MISD (specialized fault-tolerant pipelines), MIMD (multicore servers, distributed cloud clusters).
CAP theorem (Brewer's theorem)
In any asynchronous network subject to partitions (P), a distributed data store can guarantee at most two of three properties simultaneously: Consistency (C), Availability (A), or Partition Tolerance (P). Since network partitions are inevitable in cloud physical networks, architectures must trade Consistency for Availability (AP) or vice versa (CP).
Latency, throughput and fault tolerance
Latency is time for one operation; throughput is work completed per unit time. Fault tolerance means a system continues to deliver its required function despite specified failures. More workers can raise throughput yet introduce communication overhead, shared bottlenecks or new failure modes.

02 / Unit II

Service architecture and communication

See SOA and web services and messaging for diagrams and failure-handling details.

Service-oriented architecture (SOA)
An architectural approach in which independent services expose useful business capabilities through explicit contracts. Loose coupling means consumers rely on a stable interface and semantics rather than the service’s database, language or physical host.
Monolithic vs Microservices architecture
A monolith bundles UI, business logic, and shared database into a single deployable artifact. Microservices decompose functionality into independently deployable, single-purpose services communicating via lightweight APIs/events, each owning its private datastore for granular scaling and fault isolation.
Service contract and composition
A contract defines operations or resources, representations, semantics, errors and security expectations. Composition coordinates several services to deliver one workflow. It introduces partial failure, timeout and compensation concerns.
Systems of systems (SoS)
A combination of useful, independently operated and often independently managed systems producing a larger capability (Maier's criteria: operational independence, managerial independence, evolutionary development, emergent behavior, geographic distribution). Governance and incompatible meanings can be harder than connecting APIs.
Web service: SOAP vs REST
SOAP is a standardized XML messaging framework with strict envelope, headers, and WSDL contracts. REST is a resource-oriented architectural style leveraging HTTP uniform interface, statelessness, and representations (JSON/XML). Neither equates to "cloud" alone.
REST
Representational State Transfer is an architectural style defined by client–server separation, stateless interactions, cacheability, a uniform interface and a layered system; code on demand is optional. Merely using JSON and HTTP verbs does not establish compliance with the full set of constraints.
Stateless request
Each request contains enough information to be understood without stored per-client conversational state. Resources may still have persistent server-side state, such as an order record.
Publish/subscribe
A producer publishes an event to a topic or broker; each subscription receives its relevant delivery without the producer addressing every consumer. Example: order.created triggers billing and stock services independently. It does not remove message schema coupling.
Topic versus work queue
Separate subscriptions can each receive the same event (fan-out); competing workers on one queue normally divide jobs among themselves. Broker implementations differ, so state the intended delivery and ordering guarantees explicitly.
At-least-once delivery and idempotency
At-least-once delivery may repeat messages after uncertain acknowledgements. An idempotent handler avoids repeating the business effect by using a stable event ID or unique business key and a suitable transaction boundary.

03 / Unit II

Virtualization structures and mechanisms

See virtualization fundamentals, types and levels, and CPU, memory and I/O.

Virtualization
Abstraction of physical resources into logical execution environments. It supports multiplexing, isolation and provisioning, but a hypervisor alone does not constitute a cloud service.
Host, guest and hypervisor
The host supplies physical resources; the guest OS runs inside a system VM; the hypervisor allocates virtual hardware and mediates access to real hardware. Isolation remains subject to software flaws and shared-capacity limits.
System VM versus process VM
A system VM exposes virtual hardware and runs an entire guest operating system. A process VM, such as a JVM runtime, provides an execution environment for one program and ends with the program; it does not supply an independently booted guest OS.
Container versus system VM
Containers isolate processes using the host kernel; system VMs run guest kernels over virtual hardware. Containers tend to start quickly and use less per-instance overhead, but share a kernel and do not have the same isolation boundary by default.
Full versus paravirtualization
Full virtualization presents virtual hardware to an unmodified guest OS using binary translation or hardware exits. Paravirtualization uses guest-aware interfaces, such as hypercalls or virtio drivers, to reduce emulation overhead.
Hardware-assisted virtualization
CPU features such as Intel VT-x or AMD-V provide controlled guest execution (VMX root/non-root) and VM exits. EPT/NPT supply a second stage of address translation in silicon, eliminating software shadow page tables.
Popek-Goldberg virtualization theorem
An architecture is virtualizable if all sensitive instructions (those that read or alter hardware configurations) are a strict subset of privileged instructions (those that trap in user mode). Legacy x86 had 17 sensitive unprivileged instructions, necessitating binary translation until Intel VT-x / AMD-V introduced hardware exits.
Implementation levels
At ISA level (instruction interpretation/emulation like QEMU); Hardware level (hypervisors like ESXi/KVM); OS level (containers); Library level (WINE/API interception); Application level (JVM process VM).
Type-1 versus type-2 hypervisor
Type 1 (bare-metal) runs directly on host hardware (VMware ESXi, Xen, KVM). Type 2 (hosted) runs as an application above a host OS (VirtualBox, VMware Workstation).
Virtual CPU (vCPU)
A vCPU is a schedulable execution thread assigned a hardware VMCS block. The hypervisor time-slices multiple vCPUs across physical CPU cores, enabling safe CPU overcommitment.
Virtual memory and ballooning
Guest virtual addresses (GVA) translate to guest-physical (GPA) then host-physical (HPA). A balloon driver running inside the guest inflates to reclaim unused memory from the guest OS when the host experiences memory pressure.
Virtual I/O and Network virtualization
I/O uses emulation, virtio paravirtual drivers, or direct PCI passthrough / SR-IOV. Network virtualization decouples logical networks from physical cables using software-defined virtual switches (OVS) and VXLAN overlay tunnels for multi-tenant isolation.

04 / Unit II

Continuity and recovery

Read the worked recovery example before memorizing these terms.

Snapshot, backup, replication
A snapshot captures point-in-time state, often on the same storage. A backup is an independently recoverable copy, protected and restore-tested. Replication copies changes elsewhere for availability or recovery, but may also copy deletion and corruption. They solve different problems.
Recovery point objective (RPO)
The maximum tolerable data loss measured as time between the latest recoverable state and the failure. With an RPO of 15 minutes, a usable recovery point must be no older than 15 minutes at the time of failure.
Recovery time objective (RTO)
The maximum tolerable time to restore an acceptable service after disruption. RTO concerns downtime, not the age of restored data. Both RTO and RPO are design objectives, not automatic properties of VMs.
Disaster recovery tiers
Cold Standby: Basic infrastructure provisioned; data restored from backups upon disaster; slowest RTO (hours to days), lowest cost. Warm Standby: Scaled-down core services running with active replication; quick scale-up upon failover; moderate RTO (minutes to hours). Hot Standby (Active-Active): Full capacity duplicated and actively taking traffic across multiple regions; near-zero RTO and RPO, highest cost.
Failure domain
A set of components that can fail from one shared cause, such as a host, site or identity provider. Running two VMs on one host does not protect against loss of that host.

05 / Unit III

Architecture, deployment and service models

See the layered architecture, NIST roles, and responsibility comparison.

Layered cloud architecture
A teaching decomposition of user/access, service, orchestration, resource abstraction and physical infrastructure. Monitoring, identity, privacy and security span all layers. This conceptual stack is not the same thing as NIST’s five actors.
NIST reference architecture: five actors
The consumer uses the service; the provider delivers it; a broker intermediates use or delivery; an auditor independently assesses it; a carrier transports connectivity. Within the provider, NIST identifies service orchestration, cloud service management, and security/privacy.
Public cloud
Cloud infrastructure provisioned for open use by the general public. Customers retain restricted accounts and data; “public” describes potential use of the infrastructure, not unrestricted access to every resource.
Private cloud
Cloud infrastructure provisioned for exclusive use by one organization. It may be on- or off-premises and managed by the organization, a third party or both.
Hybrid cloud versus multicloud
A NIST hybrid binds at least two distinct cloud infrastructures, for example private and public, with technology enabling data and application portability. Multicloud means using more than one provider and is not by itself a NIST deployment model.
IaaS, PaaS, SaaS
IaaS: Virtualized compute, storage, networks; customer manages OS, runtime, and apps. PaaS: Managed runtime platform; customer deploys code and config. SaaS: Complete end-user application (e.g. email, CRM); customer manages users and data.
CaaS (Communication as a Service)
Cloud delivery of enterprise communications (VoIP, video conferencing, PBX, messaging) on a subscription basis, eliminating on-premises telecom PBX hardware (e.g. Twilio, Cisco Webex).
Serverless computing (FaaS)
An event-driven execution model where code runs in ephemeral stateless containers managed entirely by the cloud provider. Enhances PaaS by eliminating idle instance charges (zero billing at zero traffic) and providing instantaneous automatic scaling (e.g. AWS Lambda).
Shared responsibility
The provider secures and operates the parts it supplies; the consumer configures and protects the parts it controls. The boundary varies by service and contract, and no service model eliminates the customer’s data governance duties.
Cloud security standards
Key compliance frameworks: ISO/IEC 27001 (ISMS baseline), SOC 2 Type II (operational audit across security/confidentiality/availability), NIST SP 800-53/FedRAMP (federal agency authorization), CSA STAR (cloud controls matrix), PCI DSS (cardholder data security).
Insider threat mitigation
Threats from authorized users abusing privileges. Mitigated by Zero Trust, Least Privilege IAM policies, Privileged Access Management (PAM/JIT access), hardware MFA, and immutable Write-Once-Read-Many (WORM) audit logging.

06 / Unit III

Cloud storage and Amazon S3

See the block/file/object comparison and the S3 case study.

Storage as a service (STaaS)
Storage capacity and access supplied through a managed service rather than owned on-premises equipment. The provider maintains physical storage; the consumer manages data, access, retention and recovery requirements. Pricing can include capacity, requests, retrieval and data transfer.
Block versus file versus object storage
Block exposes addressable volumes suitable for filesystems and databases (EBS, Azure Disk); file exposes shared path-based filesystem operations (NFS/SMB, EFS); object exposes key-addressed whole objects with metadata through an HTTP REST API (S3, GCS, Azure Blob).
Durability versus availability
Durability concerns the chance of retaining stored data over a period; availability concerns the ability to access it when needed. An outage can block reads without losing bytes. Neither measure alone replaces a tested backup policy.
S3 bucket, key and object
An Amazon S3 bucket holds objects in a selected AWS Region. Each object has data and metadata and is identified within the bucket by its key. A slash in a key resembles a directory path but does not create an ordinary POSIX filesystem.
S3 storage classes and lifecycle
Classes include S3 Standard (frequent access), Intelligent-Tiering (automatic cost optimization), Standard-IA (infrequent access), and Glacier/Glacier Deep Archive (long-term archive). Lifecycle rules automate transitions between tiers and object expiration.
S3 security: policies, encryption, presigned URLs
Secured via IAM identity policies, S3 Bucket policies, Block Public Access, and encryption (SSE-S3, SSE-KMS, SSE-C). Presigned URLs grant time-limited, scoped access to download or upload specific objects without sharing credentials.
S3 consistency model
Amazon S3 provides strong read-after-write consistency for PUT and DELETE requests of objects across all regions, including atomic updates and immediate listing visibility.

07 / Exam Technologies

Extended exam technologies and platforms

Specific platforms and tools appearing in past examination papers:

Hadoop and HDFS
Apache Hadoop is an open-source distributed computing framework for storing and processing big data across commodity clusters. HDFS (Hadoop Distributed File System) splits large files into blocks (default 128 MB) and distributes them with triple replication across DataNodes, coordinated by a central NameNode for high fault tolerance and rack awareness.
MapReduce
A distributed programming model within Hadoop that processes massive datasets in parallel across clusters via three main phases: Map (filtering and transforming local input data into key-value pairs), Shuffle and Sort (grouping all values by key across the network), and Reduce (aggregating grouped values into final output results).
OpenStack
A modular open-source cloud computing platform for building public and private IaaS clouds. Key core components include Nova (compute/VM provisioning), Neutron (networking), Swift (object storage), Cinder (block storage), Glance (VM image service), and Keystone (identity/authentication).
Google App Engine (GAE)
Google's pioneer Platform as a Service (PaaS) offering that allows developers to build and deploy scalable web applications and mobile backends without managing underlying servers, featuring automatic scaling, load balancing, and integrated Datastore/memcache.
Nimbus
An open-source scientific IaaS cloud computing toolkit that allows users to lease remote computational resources through virtualization. Widely used in scientific grid and cloud computing research to dynamically deploy customized virtual clusters on infrastructure.
AWS (Amazon Web Services)
The pioneer global public cloud platform distinguished by its vast service catalogue (compute EC2, storage S3/EBS, database RDS/DynamoDB, serverless Lambda, networking VPC), global multi-region and Availability Zone infrastructure, mature enterprise marketplace, and comprehensive compliance certifications.
Cloud CRM (Customer Relationship Management)
Cloud-hosted software-as-a-service (e.g. Salesforce, HubSpot) that centralizes customer contact information, sales pipelines, marketing automation, and customer support workflows, enabling remote accessibility, real-time collaboration, and automated sales analytics.
Cloud Office Suites & Collaboration Tools
SaaS productivity platforms (e.g. Google Workspace, Microsoft 365) providing real-time multi-user document co-authoring, cloud file synchronization (Drive/OneDrive), automated revision history, centralized access control, and seamless communication across remote and in-office teams.
